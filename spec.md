# Research Assistant — спецификация и состояние реализации

## Назначение

Python-приложение принимает техническую тему, составляет план исследования,
находит источники и формирует Markdown-отчёт. Возможности добавляются постепенно;
каждый завершённый этап должен давать проверяемый результат.

## Текущее состояние

### Этапы 5 + 6 — Report Generation + Persistence

Статус: завершён; автономно проверен. Реализация в двух блоках: A — ReportDraft, проверка ID
источников, программный Markdown и атомарная запись; B — файловый SqliteSaver,
Pause и Resume между процессами. Полный режим требует review/search/report;
прежние режимы сохраняются. В State сохраняются версия Workflow, режим,
абсолютные пути БД и output-dir, thread_id; секреты и клиенты не сохраняются.
Resume проверяет get_state, версию и режим, продолжает interrupt через Command,
ошибку через invoke(None), завершённый Thread возвращает без повторного запуска.
Checkpoints синхронные. report_ready предшествует записи, completed — только
после атомарной замены файла. Cancel/no_sources завершаются без Report.
Промпт плана 1 раздел/1 вопрос/40 слов, Tavily max_results=1, snippet<=500
сохраняются; ручные планы не ограничены числом разделов.
Проверки автономные, включая два subprocess и ошибку записи с восстановлением.
API без отдельного разрешения не вызываются. Exactly-once не гарантируется:
незавершённый Node и запросы внутри search_sources могут повториться.
Academy: Research Assistant, Persistence / External Memory, Human-in-the-Loop;
предпосылки — State, Nodes, Conditional Edges, interrupt. Наличие реализации
не подтверждает изучение; Store, Long-Term Memory, Time Travel, Parallelization,
Subgraphs и Deployment не считаются пройденными.

## Этап 1 — приём темы и подготовка заявки

Статус: завершён.

### Поведение

CLI принимает обязательный аргумент `--topic`. Сохраняет исходную строку,
сворачивает последовательности пробельных символов в один пробел и удаляет
пробелы по краям. Для корректной темы выводит читаемый JSON в stdout.
Пустая после нормализации тема вызывает понятное сообщение в stderr и ненулевой
код завершения без traceback ожидаемой ошибки.

### Граф и данные

`START → validate_topic → prepare_request → END`

- `topic: str` — обязательный исходный ввод.
- `normalized_topic: str` — появляется после проверки.
- `status: Literal["ready"]` — появляется после подготовки заявки.
- `ready` означает готовность к планированию, а не завершение исследования.
- Схема состояния: `TypedDict`; выходные поля при вводе могут отсутствовать.
- `validate_topic` возвращает обновление `normalized_topic`, при пустой теме
  поднимает `ValueError`.
- `prepare_request` возвращает обновление `status`.
- Узлы не изменяют входной словарь на месте.
- Построение графа отделено от CLI; используются `StateGraph`, `compile()`, `invoke()`.
- CLI обрабатывает ожидаемую ошибку проверки, не скрывая неожиданные ошибки.

### Границы

Без модели, API-ключей, поиска, памяти, checkpointer, streaming, условных переходов,
подграфов, веб-интерфейса и требования Studio.

### Критерии приёмки

- [x] Обычная тема проходит граф и возвращает три согласованных поля.
- [x] Пробелы, табуляция и переносы строк нормализуются.
- [x] Исходное значение `topic` сохраняется.
- [x] Пустая и пробельная тема отклоняются.
- [x] CLI выдаёт читаемый JSON при успехе и ненулевой код при ошибке ввода.
- [x] README содержит установку, команды PowerShell, запуск и пример результата.
- [x] Зависимости и поддерживаемая версия Python указаны; настроен `.gitignore`.
- [x] Записаны реально выполненные проверки и их результаты.

## Этап 2 — генерация плана исследования

Статус: завершён; автономные проверки подтверждены. Реальный вызов подтверждён
для предыдущей версии; новые ограничения проверены без обращения к API.
Провайдер выбран пользователем: Польза AI (OpenAI-совместимый API).

### Требования

- Сохранить обязательный `--topic`, нормализацию, исходный `topic` и отказ для пустой темы.
- Граф: `START → validate_topic → prepare_request → generate_plan → END`.
- `generate_plan` получает `normalized_topic`, вызывает модель и возвращает только
  обновления `plan` и `status="planned"`; входное состояние не изменяется.
- `ready` означает готовность к планированию; `planned` — наличие проверенного плана,
  а не завершение исследования. `plan` отсутствует до успешной генерации.
- Pydantic-схемы `ResearchSection`, `ResearchPlan`: проверка структуры и непустых
  после strip строк. Без ограничений количества разделов, вопросов и слов.
- Краткость задаётся только промптом: 3 раздела, каждый до 80 слов
  (название и вопросы вместе). Ограничение токенов в API не передаётся.
- Инструкция модели: русский язык, соответствие теме, отсутствие повторов;
  только планирование без поиска и заявлений о выполненном исследовании.
- Использовать `ChatOpenAI.with_structured_output` с JSON Schema; сериализовать
  проверенную схему через `model_dump(mode="json")`.
- Конфигурация через `POLZA_API_KEY`, `POLZA_MODEL`, необязательный `POLZA_BASE_URL`
  (по умолчанию `https://polza.ai/api/v1/`). Не выбирать платную модель молча.
- Подключение создаётся лениво после проверки темы; тесты подставляют генератор.
- CLI обрабатывает только ожидаемые ошибки ввода, конфигурации, API и структуры:
  понятный stderr, ненулевой код, никакого успешного JSON или фиктивного плана.
- Без поиска, инструментов, памяти, checkpointer, streaming, условных переходов,
  повторной генерации, параллельности, подграфов и веб-интерфейса.
- Реальный вызов модели только при настроенном подключении и отдельном разрешении.

### Критерии приёмки

- [x] Сохранены проверки этапа 1 с учётом нового итогового статуса и плана.
- [x] Валидный план появляется в state, status становится planned.

## Этап 3 — проверка и утверждение плана человеком

Статус: завершён. Реализация по подробному заданию пользователя от 2026-10-19;
автономные проверки подтверждены, ручная проверка пользователем ещё не выполнена.

- Добавить отдельный `review_plan` после `generate_plan` с `interrupt()`.
- Продолжать тот же запуск через `Command(resume=...)`, тот же `thread_id`
  и тот же экземпляр графа с `InMemorySaver`.
- Интерактивный CLI: утвердить план, загрузить исправленный JSON-план и утвердить,
  либо отменить. Исправленный план проверять существующей `ResearchPlan`.
- Редактирование не вызывает модель повторно; вызов API остаётся в `generate_plan`.
- Итоговые статусы: `approved` и `cancelled`; исходная тема сохраняется.
- Не добавлять ограничения размеров плана, ранее отменённые пользователем.
- Сохранить прежний неинтерактивный режим планирования; ревью включать флагом
  `--review`. Без флага состояние остаётся `planned`.
- Человеческий интерфейс и ввод — в CLI; узлы не вызывают `input()`.
- Решения Python API: `{"action": "approve"}`, `{"action": "cancel"}`,
  `{"action": "edit", "plan": {...}}`; проверяются discriminated union Pydantic
  внутри узла после interrupt. Лишние поля запрещены. Неверное решение API
  вызывает ValidationError до применения обновления.
- `build_graph(..., review=True, checkpointer=...)` требует явный checkpointer.
  CLI создаёт InMemorySaver и UUID thread_id один раз на исследование.
- EOF/Ctrl+C при ожидании решения, пути или подтверждения дают cancelled и код 0.
- Неинтерактивный stdin с --review отклоняется до API; stdout можно перенаправлять.
- Неверный файл/JSON/план оставляет CLI в ожидании исправления или отмены.
- Подсказки и показ плана в review-режиме идут в stderr; итоговый JSON — в stdout.
- В этом этапе пауза живёт только в текущем процессе. Постоянное хранилище
  и восстановление после перезапуска остаются задачей этапа 6.

Критерии: проверка паузы до решения; утверждение; замена плана; отмена;
отклонение некорректного редактирования; сохранение исходной темы;
один вызов генератора при паузе/продолжении; сохранение прежнего CLI без флага;
изолированные thread_id. Проверки автономные, без реального API.

  Tavily; строки не обрезаются. Это ограничение API, а не размера самого плана.
- Source: непустой title, HTTP(S) url, строка snippet (включая пустую), список
  неотрицательных section_indexes с 0. Точные URL сравниваются как строки после
  удаления пробелов по краям; остальные различия URL не канонизируются.
- В дубликатах title/snippet первого результата сохраняются, section_indexes
  объединяются в порядке появления. Поле content Tavily отображается в snippet;
  отсутствие content даёт пустую строку, null и нестроковые значения — ошибку.
  Лишние поля ответа SDK игнорируются. Неверные источники не пропускаются молча.
- Ответ без списка results считается ошибкой (проверяется HTTP response hook
  до того, как SDK подставит results=[]). Полные страницы не загружаются.
- План без разделов даёт sources=[] и no_sources без поиска; дополнительные
  ограничения числа разделов не вводятся.

## Объединённый этап 5 + 6 — Report Generation + Persistence

Статус: завершён, автономно проверен. Существующие режимы CLI сохранены.
Persistence / External Memory здесь означает файловые Checkpoints выполнения,
а не LangGraph Store или Long-Term Memory. Разбор и практика пользователя
по этим механизмам ещё не подтверждены.

### Report Generation

- Новый режим `--review --search --report`, отдельные Nodes `generate_report`
  и `save_report` после успешного поиска. `--report` требует двух прежних флагов.
- При cancelled или no_sources завершаться без Report и без вызова модели для него.
- Модель Польза AI пишет краткий обзор только по сохранённым snippets и плану,
  без выдуманных URL, фактов и заявлений о чтении полных страниц.
- Идентификаторы источников проверять в коде; Markdown References формировать
  из фактических sources. Рекомендованный объём до 200 слов задаётся промптом.
- Сохранить текущие настройки компактности плана/Tavily и отсутствие жёсткого
  лимита выходных токенов. Отчёт требует одного дополнительного LLM-вызова.
- State: report_markdown, report_path; completed только после успешной записи.
- Файл UTF-8, детерминированное безопасное имя по thread_id, атомарная замена
  и Idempotency при повторной записи; запись отдельно от LLM Node.

### Persistence

- В report-режиме использовать файловый `SqliteSaver`, пакет
  `langgraph-checkpoint-sqlite`, контекстный менеджер на весь цикл выполнения.
- Новые опции: `--resume THREAD_ID`, `--checkpoint-db PATH`, `--output-dir PATH`,
  `--pause-after-plan` (сохранить Pause и завершить CLI без отмены).
- Дефолты: `.research_assistant/checkpoints.sqlite` и `reports/`.
- `--resume` использует прежний thread_id, тот же файл БД и совместимый Graph;
  новая тема и переключение режима сохранённого Thread не допускаются.
- Хранить несекретные параметры режима и абсолютные пути для корректного Resume.
  Ключи API в State/Checkpoint не сохранять. Новый запуск получает новый ID.
- Перед Resume вызвать get_state: Pause → Command(resume=decision),
  ошибка незавершённого Node → invoke(None, config), завершённый Thread →
  вернуть сохранённый результат без повторных внешних вызовов.
- Применять синхронное сохранение Checkpoints, если доступно в установленной версии.
- Не обещать exactly-once API calls: незавершённый Node может повториться.
  Поиск внутри одного Node при сбое может повторить запросы разделов.
- БД, её служебные файлы и reports исключить из Git.

### Приёмка

Автономные тесты с временной файловой SQLite: процесс 1 доходит до Pause и
закрывает соединение; процесс 2 создаёт новый saver/Graph и продолжает без
повторной генерации плана. Проверить Report и реальные URL, UTF-8, пустые
источники, cancel, ошибку записи с последующим Resume без повторного LLM,
неизвестный Thread, несовместимые режимы, изоляцию Threads и прежние режимы CLI.
Реальные платные запросы — только с отдельным разрешением пользователя.

Связь с Academy: Research Assistant (модуль 4), Persistence / External Memory
и Human-in-the-Loop (модули 1–3). Markdown-файл — формат результата приложения;
файловый Checkpointer не заменяет темы Store / Long-Term Memory / Deployment.
